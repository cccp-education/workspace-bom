== 2. Vision

*Le BOM devient l'unique source de vérité des versions cross-borough, transportée par artefact
Maven Central.* Un borough consomme le catalogue publié (pas le repo physique) et n'écrit plus
aucune version de plugin education.cccp en dur. Un bump MEMPHIS suffit à propager — le
consommateur ne bump que son *pin de catalogue* (1 ligne, même rythme, jamais éparpillé).

----
[MEMPHIS N0] libs.versions.toml (source unique)
     │  publish versionCatalog
     ▼
education.cccp:workspace-catalog:0.0.X  ──►  Central
     │
     │  settings.gradle.kts (pin UNIQUE par borough) :
     │    versionCatalogs { create("ws") { from("education.cccp:workspace-catalog:0.0.X") } }
     ▼
[BOROUGH N2] version = ws.versions.slider.plugin.get()
             dependencies { implementation("education.cccp:document-plugin") }  ← platform BOM fournit la version
----

=== Périmètre exact (ce que le BOM contrôle / ne contrôle pas)

[cols="2,3,3"]
|===
| Élément | Source de vérité cible | Rationale
| Versions des *plugins education.cccp* consommés (document, codebase, slider, ...) | `workspace-catalog` (MEMPHIS) | La douleur : bumps éparpillés C4
| Versions des *contracts N0* | déjà platform BOM ✅ (compléter si trous) | Pattern existant
| *Version propre* du plugin publié par le repo (ex: bakery 0.0.10) | *reste locale* (repo) | Une version d'artefact est intrinsèque à son repo (tags, release, dogfooding). Le BOM câble ENTRE artefacts, il ne possède pas la version DE chaque artefact.
| Déps tierces propres au borough (asciidoctorj-jar, jbake, ...) | `libs` local | Série de versions non cross-borough — les centraliser serait l'inverse de la bonne direction
| Le *pin* `from("education.cccp:workspace-catalog:X")` | 1 ligne locale par borough | Irréductible (Gradle refuse les versions dynamiques dans `from()` — reproductibilité) ; c'est le seul résidu, 1 au lieu de N
|===

=== Deux mécanismes Gradle natifs (complémentaires, pas exclusifs)

. *Platform BOM (existant)* — contraint les *dépendances* :
  `implementation(platform("education.cccp:workspace-bom:0.0.X"))` puis
  `implementation("education.cccp:document-plugin")` sans version. Couvre les deps
  `implementation/api` entre boroughs.
. *Version Catalog publié (nouveau)* — contraint les *versions* consultables + les
  *plugins appliqués* :
  [source,kotlin]
  ----
  // MEMPHIS build.gradle.kts — 2e publication
  create<MavenPublication>("versionCatalog") {
      versionCatalog { from(files("gradle/libs.versions.toml")) }
      groupId = "education.cccp"; artifactId = "workspace-catalog"
  }
  ----
  ----
  // Consommateur settings.gradle.kts
  dependencyResolutionManagement {
      repositories { mavenCentral() }
      versionCatalogs { create("ws") { from("education.cccp:workspace-catalog:0.0.X") } }
  }
  // build.gradle.kts : accesseurs typés générés (ws.versions.bakery.plugin.get(),
  // ws.plugins.kotlin.jvm, ws.libs.document.plugin)
  ----

== 3. Décisions architecturales (12)

[cols="1,6", options="header"]
|===
| # | Décision
| D1 | *2 artefacts MEMPHIS* : `workspace-bom` (platform, existant) + `workspace-catalog` (nouveau, publication `versionCatalog` du toml). Même repo, même release, même bump.
| D2 | *Périmètre catalog* : les 12 plugins `education.cccp:*` + les versions partagées cross-borough. HORS SCOPE : déps tierces propres (asciidoctorj, jbake, playwright) — elles restent dans `libs` local ou dans la platform.
| D3 | *Version propre d'un plugin* : reste dans son repo (règle « le BOM câble entre, pas dedans »). Le test d'hygiène type `BakeryPluginPublicationTest` évolue pour vérifier `version = ws.versions.<self>.get()` au lieu d'un toml local dupliqué.
| D4 | *Pin unique* : chaque consommateur garde exactement 1 version locale — `from("...workspace-catalog:0.0.X")` dans settings. Pas de version dynamique (reproductibilité, D-Gradle).
| D5 | *Adoption paresseuse* : un borough peut rester sur son ancien câblage tant qu'il veut. Migration borough par borough, jamais big bang.
| D6 | *`libs` local conservé* pour les aliases spécifiques au borough ; les aliases cross-borough migrent sous `ws` (collision impossible — préfixes distincts).
| D7 | *Plugin `id(...) version`* (C7) : les consommateurs qui appliquent les plugins via block `plugins` passent à `alias(ws.plugins.bakery)` — couvert par le catalog, pas par la platform. US dédiée (le changement est dans `build.gradle.kts` racine des consommateurs).
| D8 | *Boroughs jamais publiés* (capsule 0.0.1-SNAPSHOT, jhipster SNAPSHOT) : entrée catalog = fantôme non résolvable depuis Central. Décision : l'entrée est créée au moment de la première publication Central (pas avant) — le catalog ne référence que du résolvable.
| D9 | *Publication* : le catalogue suit le cycle release du BOM (même commit, même bundle nmcp). Vérifier que nmcp 1.5.0 agrège les 2 publications du module racine (déjà le cas pour les 8 modules contrats → oui, `publishAggregationToCentralPortal` est aggrégatif).
| D10 | *Anti-split-brain* : une US dédiée supprime la divergence intra-MEMPHIS (C1/C2) — la platform `build.gradle.kts` consomme le toml via `libs.*` AU LIEU de hardcoder (les lignes 19-125 deviennent `api(libs.kotlin.stdlib)` etc.), et la version BOM est dérivée du toml (`version = libs.versions.workspace.bom.get()`).
| D11 | *Tests de garde* : (a) UT structurels sur le catalogue publié (chaque plugin résolvable, versions non-vides) ; (b) FT consommateur pilote (`ws` accessor compile + résout depuis Central/mavenLocal) ; (c) test d'hygiène « pas de version hardcodée education.cccp dans build.gradle.kts des consommateurs migrés » (grep-like).
| D12 | *Zéro couplage physique au repo BOM* : la transmission est Maven (Central + mavenLocal), jamais `includeBuild` ni chemin de filesystem — c'est la demande explicite du pilote.
|===

== 6. Hors périmètre (explicite)

- *Version propre des plugins* (chaque repo garde sa release — D3).
- *conventions-gradle* (`includeBuild`, pas de résolution Maven).
- *Migration des autres boroughs* (généralisation post-EPIC, borough par borough).
- *Déps tierces borough-spécifiques* (restent locales).
- Le *bump de versions réelles* des plugins (l'EPIC installe le MÉCANISME ;
  les bumps restent des actes de release pilotés).
